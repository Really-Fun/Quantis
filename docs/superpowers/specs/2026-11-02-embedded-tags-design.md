# Теги и обложки внутри скачанных треков — дизайн

Дата: 2026-11-02

## Зачем

Скачанный в Quantis трек должен быть полноценным музыкальным файлом, который
можно забрать из папки и слушать где угодно: в другом плеере, на телефоне, в
проводнике. Сейчас это голый mp3/m4a с именем `ID_Название_Исполнитель.mp3`,
без тегов и без обложки внутри — вне Quantis он выглядит как мусор.

Вторая (менее важная) цель — красивая папка в проводнике Windows: обложка как
иконка файла, название/исполнитель/альбом/жанр в подсказке при наведении и в
колонках.

## Текущее состояние (на коммите 9860e34)

- Форматы: Яндекс — mp3 (320 / 192 без авторизации), YouTube — m4a или mp3
  (`_AUDIO_FORMAT` в `services/async_downloader.py` уже исключает webm/opus),
  SoundCloud — mp3. Перекодирование не нужно: проводник и плееры полноценно
  читают теги и обложки в mp3 и m4a.
- Теги не пишутся вообще: у yt-dlp пустые `postprocessors`, Яндекс отдаёт mp3
  без ID3.
- Обложка качается отдельным jpg в папку covers (`PathProvider.get_cover_path`),
  интерфейс берёт её оттуда.
- Имя файла `{storage_id}_{title}_{author}.{ext}` (`PathProvider.get_track_path`).
  ID в начале имени — несущий. На нём держатся:
  - `TrackManager._load_ids` — «скачан ли трек»;
  - `PathProvider.find_track_file` — поиск файла для воспроизведения;
  - `DownloadPlaylist.delete_track` — удаление (glob по префиксу);
  - `DownloadPlaylist.get_tracks_from_music_dir` — список «Скачанные»
    (id/название/автор разбираются из имени);
  - `_apply_downloaded_extension` у YouTube/SoundCloud загрузчиков — поиск
    файла после yt-dlp.
- Пользователь может выбрать свою папку музыки (`storage/music_dir`).
- Места, где запускается скачивание: `ui/views/player_bar.py`,
  `ui/viewmodels/search_vm.py`, `ui/viewmodels/home_vm.py` — везде
  `download_track`, затем `download_cover`.

## Цели

1. После скачивания в файл вшиваются: обложка, название, исполнитель, а если
   источник отдаёт — альбом, исполнитель альбома, год, жанр, номер трека.
2. В поле «Комментарий» — ссылка на трек в источнике (видна в проводнике).
3. В служебное поле — источник и ID трека (по нему Quantis узнаёт свой файл).
4. Новые загрузки называются по-человечески: `Исполнитель - Название.mp3|m4a`.
5. Quantis находит свои файлы по служебному тегу, а не по имени — значит
   переименованный пользователем файл тоже находится.
6. Кнопка в настройках дописывает теги и переименовывает уже скачанные треки.

## Не цели

- Не меняем формат и качество звука, не перекодируем, не тянем ffmpeg.
- Не выдумываем данные: нет жанра (типично для YouTube) — поле пустое.
- Текст песни (lyrics) — не в этой задаче.
- Чужие файлы без наших тегов (своя музыка, закинутая в папку) Quantis не
  показывает. Это осознанно и устраивает (решено с пользователем).
- Не меняем, откуда интерфейс берёт обложку: jpg в covers остаётся.

## Анти-цели (провал, даже если «работает»)

- Трек, скачанный успешно, считается нескачанным или пропадает из «Скачанных»
  из-за ошибки записи тегов или переименования.
- Старые файлы `ID_…` перестают находиться до нажатия кнопки.
- Кнопка переименовывает файл, в который не удалось записать ID, — и Quantis
  его теряет.
- Заметно медленнее стартует приложение на большой папке.
- Падение приложения при битом/чужом файле в папке.

## Решения

### Запись тегов

- Библиотека: **mutagen** (чистый Python, без ffmpeg, просто собирается в
  PyInstaller). *Решение Claude.*
- mp3: ID3v2.3 (проводник Windows читает её надёжнее v2.4). *Решение Claude.*
  - TIT2 название, TPE1 исполнитель, TALB альбом, TPE2 исполнитель альбома,
    TYER/TDRC год, TCON жанр, TRCK номер трека, APIC обложка (front cover),
    COMM — ссылка на источник, TXXX — служебные поля.
- m4a: стандартные атомы (`©nam`, `©ART`, `©alb`, `aART`, `©day`, `©gen`,
  `trkn`, `covr`, `©cmt`) + freeform-атомы `----:com.quantis:…` для служебных.
- Служебные поля: `QUANTIS_SOURCE` (`yandex|youtube|soundcloud`) и
  `QUANTIS_ID` (id как в `track_id`; для SoundCloud — числовой id, без `sc`).
  Точное имя ключей — на усмотрение исполнителя, но оно должно быть одним
  для mp3 и m4a и зафиксировано константой.
- Вшиваем ту же обложку, что уже скачивается в covers (Яндекс 400×400,
  YouTube maxres/sd/hq, SoundCloud thumbnail). *Решение Claude.* Если jpg нет
  или он битый (`cover_file_ok`) — теги пишутся без обложки.
- Порядок: скачать трек → скачать обложку → записать теги → переименовать.
  Где именно это склеить (в `AsyncDownloader` или отдельным сервисом,
  вызываемым из трёх мест скачивания) — на усмотрение исполнителя, но
  предпочтительно одно место, а не три копии.
- Ошибка записи тегов не делает скачивание неуспешным: пишем в лог, файл
  остаётся (с каким получилось именем), трек считается скачанным.

### Откуда брать данные

- Название, исполнитель, обложка — есть у всех трёх источников.
- Яндекс: альбом, год, жанр, номер трека, исполнитель альбома — из объекта
  трека/альбома `yandex-music` (`client.tracks(...)` уже вызывается в
  загрузчике; если для жанра/года нужен отдельный запрос альбома — допустимо
  один лишний запрос, с учётом существующих мер против лимита Яндекса, см.
  `test_yandex_rate_limit.py`).
- SoundCloud: жанр и год — из info yt-dlp (`genre`, `upload_date`/`release_date`).
- YouTube: альбом/год, если info yt-dlp их отдаёт (`album`, `release_year`,
  `artist` для YouTube Music); жанр обычно нет — оставляем пусто. Исполнителя
  чистим тем же `strip_youtube_stats`.
- Ссылка на источник: Яндекс `https://music.yandex.ru/track/{id}`, YouTube
  `https://music.youtube.com/watch?v={id}` (или youtube.com — на усмотрение),
  SoundCloud — `services.soundcloud.watch_url` / permalink.
- Для yt-dlp сейчас `extract_info` вызывается с `download=True`, и info
  отбрасывается — его надо вернуть наружу, чтобы не делать второй запрос.

### Имена файлов

- Новый шаблон: `{Исполнитель} - {Название}.{ext}`.
- Запрещённые символы заменяются как сейчас (`_sanitize_filename_part`).
- Совпадение имени (тот же трек из другого источника, одноимённые треки):
  добавляется ` (2)`, ` (3)`… Файл, который уже принадлежит этому же треку
  (тот же source+id в тегах), — перезаписывается, а не дублируется.
- yt-dlp пишет во временное имя (можно оставить старый шаблон `ID_…` как
  временный), переименование — после записи тегов. Если теги записать не
  удалось — файл **не** переименовывается и остаётся с именем `ID_…`, чтобы
  его находила старая схема.
- Учитывать предел длины пути Windows (обрезать очень длинные имена) —
  *решение Claude*, конкретный лимит на усмотрение исполнителя.

### Как Quantis находит свои файлы

- Индекс `(source, id) → путь`, строится сканированием папки музыки:
  - файл с нашими служебными тегами → по тегам;
  - файл без тегов, но с именем `ID_…` → по старой схеме разбора имени
    (как сейчас в `TrackManager` и `get_tracks_from_music_dir`);
  - остальное игнорируется.
- Список «Скачанные» берёт название/исполнителя из тегов, если они есть;
  иначе из имени по старой схеме.
- Все пять мест из «Текущего состояния» переводятся на индекс (единая точка
  правды), а не каждое со своим glob'ом.
- Индекс обновляется при скачивании, удалении, работе кнопки и смене папки
  музыки.
- Скорость: чтение тегов на большой папке не должно заметно тормозить старт и
  не должно идти в UI-потоке. Кэш индекса на диске (ключ — имя файла + размер
  + mtime) — на усмотрение исполнителя; требование только «старт не стал
  заметно медленнее на ~1000 треков».
- Удаление трека удаляет файл, найденный через индекс (любое имя), и jpg
  из covers.
- Холодный старт. `TrackManager.is_downloaded` синхронный и вызывается из
  `track_builder.build_track` везде (поиск, главная, история, лайки).
  Решение (*Claude*): кэш индекса на диске **обязателен**; при старте он
  читается синхронно (это быстро, тегов не читаем), затем в фоне
  сверяется с папкой (новые/изменённые файлы по размеру+mtime дочитываются
  из тегов). Без кэша (первый запуск после обновления, смена папки) —
  короткое неверное «не скачан» допустимо, но конвейер скачивания перед
  выбором имени файла **ждёт готовности индекса**, чтобы не появлялись
  дубликаты `(2)` для уже скачанного трека. После фоновой сверки UI
  получает сигнал и обновляет «Скачанные» и значки.

### Успех скачивания

- Конвейеру нужен реальный путь к файлу и реальный признак успеха, поэтому
  загрузчики возвращают результат (путь или None) вместо молчаливого
  `None`. *Решение Claude.*
- Баг: `AsyncYoutubeDownloader._apply_downloaded_extension` делает
  `Path(self.path_provider.MUSIC_FOLDER)`, а `MUSIC_FOLDER` вне тестов
  `None` → TypeError, исключение глушится, и `_download_audio` возвращает
  False даже при скачанном файле. Чинится в рамках задачи (использовать
  `music_folder()`, как у SoundCloud).
- Неудачное скачивание больше не помечает трек скачанным: три места вызова
  (`player_bar.py`, `search_vm.py`, `home_vm.py`) ставят
  `downloaded = True` только при успехе, чтобы кнопка позволяла повторить.
  Тесты этих мест обновляются. *Решение Claude.*
- Единая точка входа «скачать трек целиком» (трек → обложка → теги →
  имя → индекс) вызывается из всех трёх мест вместо пары
  `download_track` + `download_cover`.

### Кнопка в настройках

- В `ui/views/settings_page.py`, рядом с настройками папки музыки. Название
  вроде «Записать теги в скачанные треки» — формулировка на усмотрение.
- Проходит по всем нашим трекам в папке (из индекса), для каждого:
  1. запрашивает у сервиса недостающие метаданные (альбом/год/жанр);
  2. при необходимости докачивает обложку (`ensure_cover`);
  3. пишет теги и обложку;
  4. переименовывает в `Исполнитель - Название`.
- Прогресс «обработано N из M», UI не замерзает, работу можно спокойно
  пережить (закрытие окна посреди процесса не портит файлы — запись тегов
  и переименование атомарны на уровне одного файла).
- Если сеть/сервис не ответил — пишем то, что есть локально (название и
  исполнитель из имени, ID, источник, обложка из covers). Переименовываем
  только если в файл записаны как минимум ID и название; иначе трек
  пропускается и считается в итоге как «пропущено».
- В конце — короткий итог: «готово N, пропущено K».
- **Файлы, в которых уже есть наши служебные теги, кнопка не трогает
  совсем** — ни теги, ни имя. Так не затираются переименования и правки
  тегов, сделанные пользователем в проводнике или другом плеере. Кнопка —
  это миграция только для старых файлов `ID_…` без наших тегов. Повторное
  нажатие безопасно: обработанные в прошлый раз файлы просто пропускаются
  (в итоге считаются как «уже готово», отдельно от «пропущено»).
  *Решение Claude по умолчанию (на вопрос пользователь ответил «хорошо
  делаем» без выбора варианта) — пользователь может поменять.*
- Повторное скачивание трека, у которого уже есть файл с нашими тегами,
  тоже не перезаписывает его теги и имя. *Решение Claude.*
- Разбор старых имён `ID_…`: YouTube-ID может содержать `_`, поэтому
  `split("_")[0]` ненадёжен. Для YouTube берём первые 11 символов и
  проверяем `is_youtube_video_id` (и что за ними идёт `_`); Яндекс — цифры
  до первого `_`; SoundCloud — `sc` + цифры. Если ID нельзя однозначно
  извлечь — файл пропускается и не переименовывается. Тот же разбор
  используется в индексе. *Решение Claude.*
- Темп запросов к Яндексу — с учётом существующих ограничений, чтобы не
  упереться в лимит на сотнях треков.

## Ограничения

- Python-проект, PySide6 + qasync, сборка PyInstaller под Windows (+ Linux).
  mutagen добавляется в `pyproject.toml` и должен попасть в сборку.
- Тесты — pytest (`tests/`). Существующие тесты на `find_track_file`,
  downloader и т. п. должны остаться зелёными или быть обновлены осознанно.
- Писать на диск атомарно (как `_write_cover_file`: через `.part` + replace),
  где это возможно.

## Оставлено исполнителю

- Структура модулей (отдельный `services/track_tags.py` или подобное).
- Формат и место кэша индекса.
- Точные ключи служебных тегов, текст кнопки и итогового сообщения.
- Выбор youtube.com vs music.youtube.com в ссылке.
